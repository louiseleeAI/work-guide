# 高性价比打工指南 · 方案框架

> 参考站点：https://howtolivebetter.net/（高性价比人生指南）
> 本文档只讨论思路与框架，确认后再动手搭建。

---

## 一、参考站解剖：它真正的护城河是什么

原站有 665 条建议、34 个章节、11 个功能。剥掉外观后，它的骨架是三件事：

### 1. 一套可计算的计价框架

每条建议都被强制拆成两个方向：

| 方向 | 字段 | 取值 |
|---|---|---|
| 换回什么 | 收益类型 | 寿命 / 时间与精力 / 金钱 / 人身自由 |
| 花掉什么 | 成本 | 钱 / 时间 / 毅力 |
| 凭什么信 | 证据等级 | A 随机试验·大样本 / B 观察研究 / C 经验做法 |
| 值得吗 | 性价比档 | 极高 / 高 / 一般 |

### 2. 一条铁律：不许跨口径换算

原站明确写了：省下多少钱和减少多少风险，不能排在同一把尺子上。省下的钱不等于寿命，不做折算。

这条约束是整个内容可信度的来源，也是原站最值得抄的东西。

### 3. 内容组织采用生命周期编排

不按学科分类，按读者所处的**阶段**分类，读者一进来就知道该读哪几章。

## 二、打工场景的关键差异：建议是有阈值的

这是本项目与原站最重要的区别，也是必须做对的地方。

原站的建议基本是普适的——系安全带对所有人都划算。
但打工领域的绝大多数决策**有阈值**：

- 接不接私活
- 要不要考个证
- 要不要为了 20% 涨幅搬城市
- 要不要读在职研究生
- 要不要接受一份降薪但转型的工作

同一个动作，对月薪 4k 的人是浪费，对月薪 4w 的人是救命。
如果照搬原站「一条建议一个性价比档」的写法，打工指南会立刻退化成职场鸡汤。

### 对策：每条建议必须先算阈值线

新增字段（详见第三节）：**「你的时薪 ≥ X 元 / 小时，这条才值得做」**

判定逻辑：
```
值得投入  ⟺  该动作的预期收益 / 占用工时  ≥  你当前的时薪
```

这条规则把「性价比」从形容词变成了可代入的数字。

## 三、条目数据模型

在原站字段基础上扩展，每条建议统一采用以下结构：

| 字段 | 说明 |
|---|---|
| `id` | 稳定 ID，形如 `work-06-09`。内容可改，ID 不变，保证用户标记不丢 |
| `chapter` | 所属章节编号 |
| `title` | 标题写成动作，不写道理。例：「别把公司给的内��福利算进总包」 |
| `summary` | 结论前置，一句话说完 |
| `threshold` | **核心差异字段。阈值线：时薪 / 工龄达到多少才值得做** |
| `cost` | 三档：钱 / 时间 / 毅力（沿用原站） |
| `benefit` | 三档：现金流 / 工龄复利 / 议价权（打工版收益口径） |
| `evidence` | A / B / C 三级（详见第五节） |
| `appliesTo` | 适用人群与不适用人群 |
| `source` | 法条条款 + 文件生效日期，或官方统计出处 |
| `note` | 备注：例外情况、地区差异、口径限制 |

### 打工版的三种收益口径（互不换算）

1. **现金流** — 到手月薪、年总包、折算时薪
2. **工龄复利** — 社保年限、公积金、退休金缴纳基数
3. **议价权** — 可迁移能力、稀缺度、被替代成本

沿用原站铁律：这三种收益不互相折算，不合成一个总分。

## 五、证据等级：按本项目口径重新定义

用户选择「以法条与官方数据为准」，因此沿用A/B/C 三级形式，但重新定义覆盖范围：

| 等级 | 定义 | 打工场景对应来源 |
|---|---|---|
| **A** | 查得到具体数字 | 现行法条及其实施条例、国家统计局数据、社保与个税官方文件、上市公司财报 |
| **B** | 有依据但缺精确数字 | 官方政策文件、行业调查汇总、上市公司集体行动公告 |
| **C** | 经验与通行做法 | 从业者共识、行业惯例，作者明确标注「这条没有官方依据」 |

**注意**：原站自己声明「性价比档是按原书标准只算 C 级」，即档位判断本身不是统计结论。
本项目沿用此诚实声明。

### 法条内容的时效性管理
- 每条法条必须标注**文件生效日期**
- 政策类条目单独打标���，页面顶部提示「本条依据 X 年 X 月生效版本」
- 涉及���方���定时，明确写「以你所在统筹地区当年公布为准」

| 页面 | 说明 |
|---|---|

| 检索页 | **主入口**。可按关键词、章节、证据等级、收益口径、是否有阈值线组合筛选 |

### 新增（针对打工场景）
| 页面 | 说明 |
|---|---|
| **到手测算器** | 输入月薪、社保基数、公积金比例、城市 → 输出到手金额、真实时薪、社保复利。条目中的阈值线直接复用这里的用户数据 |
| **真实时速器** | 输入税前时薪与加班时长 → 输出「你这一小时值多少钱」，用于判断是否接私活、是否值不值得加班 |

## 七、技术选型建议

- **形态**：完整静态站（用户已确认）。纯静态、可离线、无需后端
- **框架**：Vite + React（或 Astro，内容站优先考虑 Astro 的静态输出能力）
- **样式**：手写 CSS + CSS 变量，不引UI 框架。理由：条目卡片的结构高度定制，组件库反而碍事
- **数据**：条目以结构化文件（JSON / YAML）存放，一条一文件或按章分文件。改条目即改数据，检索页直接读数据
- **状态**：localStorage 存测算器输入与决策台账。首版不做登录
- **部署**：构建产物为纯静态文件，可任意静态托管

## 八、分期计划

### 第一期：地基 + 内容样板（验证这套框架立不立得住）
- 数据模型落地（条目 schema + 校验）
- 四个核心页面：首页、检索页、章节页、条目详情
- **完整写出 3 个章节**（建议选：offer 总包拆解、加班的真实时薪、竞业协议）作为内容样板
  - 这三章覆盖了三种收益口径，且法条密度最高，最能检验框架
- 阈值线字段的呈现方式定稿

### 第二期：工具
- 到手测算器 + 真实时速器
- 与条目阈值线打通（用户填一次数据，全站条目自动判定「你值不值得做」）
- 留下还是走决策表

### 第三期：填充内容 + 收口
- 补齐剩余章节
- 反面清单
- 我的决策台账

### 关于内容的产能说明
第一期三章样板是整个项目的成本大头。框架如果站得住，剩余章节可以按同一模板推进；如果站不住，早发现比写完 28 章再返工划算得多。

## 九、需要确认的三个问题

1. **阈值线的默认口径**：以「时薪」为主，还是同时提供「时薪」「工龄」「总包」三套阈值？
2. **到手测算器的城市粒度**：全国统一按社保分档算，还是做到主要城市逐个配置？
3. **是否需要克制的免责声明**：涉及劳动法与仲裁的条目，是否在每条底部加统一的免责提示？
